# Authorization details narrow access per database and per table

Status: amends [0006](0006-agents-capped-by-scope.md) and [0007](0007-pgauth-decides-from-role-bindings.md).

A token may carry an RFC 9396 `authorization_details` claim. Its rows of type `oidc.detailsType` (default `postgres`) narrow what the bindings, capped by scope, already allow: a consent row sets read or write on `*` or one `<instance>/<db>` (the most specific identifier wins), and a run row lists `<schema>.<table>` × `select|insert|update|delete`, after which that database reaches only those tables. pgauth caps by bindings ∩ scope cap ∩ the rows in the token, nothing else: when the token holds a consent row (its own, else `*`) and table rows for a database, verbs above that consent level are dropped, as are verbs above the bindings or scope. A narrowed run token usually carries only its run rows; that a run stays within the person's consent is the issuer's guarantee (it refuses a superset at narrowing), not something pgauth can check without the consent rows. A database the claim leaves with nothing is refused, and any unknown field, wrong location or malformed row refuses the token, so later restrictions cannot be silently ignored. A token without the claim gets exactly the access 0007 describes.

Table rights come from shared group roles `<rolePrefix>t_<sha16(db,schema,table,verb)>` (NOLOGIN, the verb on the table, USAGE on its schema and, for insert, on its owned sequences), created and granted only when the catalog shows them missing and never dropped; a temporary role joins them instead of `<db>_read`/`<db>_write`, so it still gets rights only through groups and dropping it ends them (0003, 0012). We chose groups over granting the temporary role directly because a direct grant would need per-table cleanup before `DROP ROLE`. The issuer login therefore needs the table, schema and sequence privileges `WITH GRANT OPTION`; it is not given them through `<db>_write`, since every write role would then be able to re-grant. The verb is granted literally: an `UPDATE` or `DELETE` with a `WHERE` also needs `select` on that table.
